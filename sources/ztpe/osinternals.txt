   1. Introduction
This document contains a description and comparison of the various Disk Operating Systems (DOS) that are
available for the TWIN. It is a companion to the various Operator Manuals and aims to combine the most
relevant sections from these manuals. Writing down the information in different words also helps really
understanding what you are writing about, and helps in discovering which bits of information are unclear or
missing, even when the original manuals gloss over these issues.
This document focuses on software; for detailed descriptions of the hardware see the system reference
documents from Signetics, Millennium and Tektronix.

 So far this manual is mostly based on SDOS2, TOS and in part on SDOS4. EXOS and TekDOS will be
         added at a later date.


Not all DOS versions are still available. SDOS 3 and the UDOS family are probably lost as no disk images
are available for them online. All sources have been lost as well except for some snippets, and source code
had to be reverse engineered.
Not all DOS features are present in all versions and some features are unique to a specific version. This
document takes care to note those differences, by the mark (version only), where version can be:
family               meaning
TOS                  applies to TOS only
EXOS                 applies to EXOS only
TOS+                 applies to TOS as well as EXOS
SDOS                 applies to all known versions of SDOS
TEKDOS               applies to all known versions of TEKDOS
A family can be followed by a number, to indicate a specific version. When a version is followed by a plus-
sign this means "this version and up"; a minus-sign means "up to and including this version, but not later
versions". For example SDOS2- includes SDOS1 and SDOS2; SDOS3+ includes SDOS3 and SDOS4.

This manual uses the following conventions for notation. Items between (parentheses) are optional: they may
appear zero or one time. Items between [square brackets] are optional and may be repeated: they may appear
zero or more times, as often as desired.
For example, with the following
         apple ( horse cherry )
         pear [ dog tree ]
some valid strings are
         apple
         apple horse cherry
         pear dog tree dog tree
Any text is to appear literally, except for parameters enclosed in «chevrons». You must use upper case only.


Numerical constants are always decimal, so "10" means ten, not sixteen. Signetics notation is used for
hexadecimal numbers: h'10' means sixteen.


Some smaller notes on notation.
   • The terms "disk" and "diskette" are used interchangeably.
10                                                                                         Introduction 1.


     •   The terms "procedure" and "command file" are used interchangeably.
     •   In DOS the term "abort" means a clean, graceful completion, not an abrupt cancellation.
     •   Manuals from Signetics, Millennium and Tektronix use the terms ‘master’ and ‘slave’ extensively.
         These terms are no longer in common use. However, for clarity we continue the use this obsolete
         terminology instead of their equivalents ‘primary’ and ‘secondary’.

   2. System commands
A system command consists of a command code followed by a number of operands, separated by spaces
and/or commas:
        «cmdcode» [ «sep» «operand» ]
The command code may be preceded by a number of spaces. Spaces following a separator (this is the
comma or space next to the command code or an operand) have no meaning: the subsequent operand starts
with the next non-space character.
To skip an optional parameter and to still supply a subsequent parameter use two commas. For example, to
supply only parameters 1 and 3 to a command CMD use
        «cmdcode» «first param»,,«third param»
A procedure is a text file containing system commands: one command per line. Procedures are also called
"command files". Procedures can be executed as if they were normal system commands. If a command line
is read from a procedure, the strings of 2 characters beginning with '$' are processed as follows:
      $D (TOS+ only)
          The string $D is replaced by the current date;
       $T (TOS+ only)
        The string $T is replaced by the current time;
       $«n»
        The string $«n» is replaced by the procedure parameter designated by «n». The serial number of
        the procedure parameter is given by the 4 least significant bits of the ASCII representation of «n».
        «n» does not need to be a decimal number. This means that $1, $2, $3 is equivalent to $A, $B, $C.
Most system commands can be abbreviated. The abbreviated format comprises only the first few characters
of the full format. In the following sections the abbreviated form is marked by underlining, for example:
        ABORT
All characters after the underlined part are optional (but must match the full format). The same notation is
used for parameters, but here often (but not always) only their underlined characters are tested, and the
remainder of the parameter is ignored.
EXOS only: Several system commands require an address. Such an address may be given in the form of an
addition:
        «hexnumber» [ + «hexnumber» ]
The value of any term and the expression shall be in the range 0 – h'FFFF'. Leading zeros are allowed.


The system commands are partitioned into the following groups:
    • System control keys and commands, 2.1;
    • System commands, 2.2;
    • Procedure utilities, 2.3;
    • Diskette and file utilities, 2.4;
    • Object program utilities, 2.5;
    • Debug commands, 2.6;
    • PROM programming utilities, 2.7;
    • Miscellaneous commands, 2.8.

        The user can control program execution by means of the Esc key and space bar, and the control commands:
                 ABORT
                 CONT

        2.1.1 Esc-key
        The Escape-key can be used to request attention of DOS. The reaction to Esc depends on the program that is
        currently running.
            • Some programs actively monitor the last character entered on the console, and terminate when Esc
                 is seen. Such programs include RHEX, LDIR and EXAM. DOS variable LastConInput can be
                 inspected, but there is also a SVC function srbFnLastChar, which is essentially the same.
             •


        Old section below.
        The ESC-key can be used to request attention of the operating system. The system reactions depend on the
        use of the console:
            1. Console in use for BINARY input:
                 No system reaction.
            2. Console in use for ASCII input:
                 EOL is returned as the only entered character, see further below.
            3. Console not in use:
                 1. First ESC:
                      A "prompt" will be issued on first occasion.
                 2. Second ESC:
                      An active job 1, an active job 3 and an active procedure are suspended; while an active job 2 is
                      aborted. Next a "prompt" is issued.
        A suspended jobs can be resumed by means of the system command CONT.

2.1.2   Space bar
        The space bar can be used to control the console output when the console input is not in use. Depressing the
        space bar once will stop output to the console; a second depression of this bar resumes the console output.

2.1.3   ABORT, CONT, SUSPEND and SUS
                 SUSPEND «name»
                 SUSPEND *
                 SUSPEND /
        This command suspends the execution of active programs. The Debug program may not be suspended. Job 2
        cannot be suspended, continued or aborted: when the Esc-key is pressed on the console an active job 2 is
        always aborted.
        SUSPEND «name» suspends the specified program or procedure. SUSPEND * suspends all active programs.
        SUSPEND / suspends the slave program.
        The primary use for this command is in conjunction with the procedure capability. Inserting this command in
        a procedure will suspend system operation to allow some required user action, such as inserting a special
        diskette into one of the drives.
        EXOS only: The command is abbreviated to SUS.
                 CONT «name»
                 CONT *
                 CONT /
        The CONT command continues the execution of a suspended program. The meaning of the parameters is the
        same as for SUSPEND.

        A suspended program may be continued by entering the CONT command. Execution of the suspended
        program resumes from the point where execution was suspended.
        Job 2 cannot be suspended, continued or aborted: when the Esc-key is pressed on the console an active job 2
        is always aborted.
                ABORT «name»
                ABORT *
                ABORT /
        The ABORT command terminates execution of an active program. The meaning of the parameters is the same
        as for SUSPEND. When terminating the DEBUG program, any active active job 2 and slave job are terminated
        as well.

        EXOS only: These commands can be used to control the state of job 1, job 3 and the procedure. The
        operands are optional. When the operands are omitted, the command concerns job 1, job 3 and the
        procedure. The possible operands are:
                1: job 1
                3: job 3
                P: procedure
        Job 2 cannot be suspended, continued or aborted: when the Esc-key is pressed on the console an active job 2
        is always aborted.
        The operands may be supplied in any sequence and more than one operand is allowed. SUSP suspends the
        execution of the designated job, CONT restores the suspended jobs to their preceding states and ABORT
        terminates jobs.

2.2.1   ASSIGN and CLOSE
                ASSIGN «channel» «device» [«channel» «device»]
        This command causes the connection of the logical slave channel «channel» to the specified «device».
        «channel» must be in the range 0-7. «device» must be one of the system device names or the name of a
        disk file.
        14                                                                                     System commands 2.2


        The ASSIGN command views every disk file as an independent physical device. When a disk file name is
        used as «device» in the ASSIGN command, the directory of the diskette is searched for the filename. If the
        filename is not found, the file is created in the directory.
        The specified channel is connected to «device», Which results in all subsequent I/O operations on the
        channel being performed on «device».
        A user application (slave) program may have only 7 of the 8 assignable channels assigned to files. When the
        command is executed from within a procedure file, only 6 channels may be assigned to disk files.
                  CLOSE «channel» [«channel»]
        The CLOSE command disconnects the channel from the device that was connected to it by the ASSIGN
        Command. If the channel was assigned to a disk file the data remaining in the SDOS deblocking buffer is
        written to the file before closing.
        The channel number must be in the range 0-7.

2.2.2   CLOCK
                  CLOCK ON
                  CLOCK OFF
        UDOS only: This command enables or disables the 100 msec real time clock interrupt. The real time clock is
        synchronized with the system clock and is available out of master memory for use by slave programs and
        other purposes. Default value of CLOCK is ON.

2.2.3   DRT
        SDOS4+ with Hardware Analyzer only: displays the Real-Time Trace buffer.
                  DRT («device») («filename»)                          (Display Mode Form)
                  DRT «filename»                                       (Storage Mode Form)
        The DRT Command is used to display the contents of the Real-Time Trace (RTT) buffer. The information is
        displayed in an easily readable ASCII format. The display may be directed to a specified output device (not a
        file).
        Alternatively, the RTT buffer contents may be transferred in binary RTT-buffer image format (saves disk
        space) onto a given disk file for storage. It may subsequently be displayed from the file to a non-file ASCII
        device.
        «device»         This optional parameter is a non-file ASCII output device. The default is CONO.
        «filename»       In display mode this optional parameter is the name of a disk file which contains an RTT
                         image generated by the DRT command in the Storage Mode Form. The default is to use the
                         current contents of the RTT Buffer.
                         In storage mode this parameter specifies the filename and drive number to which the
                         contents of the RTT buffer will be transferred.
        In display mode:
             1. If «filename» is given, the current contents of the RTT buffer and HWA database will be
                 overwritten by the information from the file and then the display will proceed.
             2. If «filename» is not given, the display will reflect the current contents of the RTT buffer and the
                 HWA database.

2.2.12 RTT
      SDOS4+ with Hardware Analyzer only: arms and disarms the Real-Time Trace function.
               RTT («option») («address») («count»)
      The Real-Time Trace command RTT is used to "arm" and "disarm" the real-time trace feature of the
      hardware analyzer card. When armed, the trace buffer memory stores the state of the slave processor
      address, data, and control lines during each bus cycle user of program execution. This process continues
      until either emulation is ceased (by the operator hitting the ESC key) or a specified "trigger" condition is
      encountered. The contents of the trace buffer may then be examined via the DRT (Display Real-time Trace)
      command to determine the sequence of events which led up to the occurrence of the trigger condition.
      The trigger condition consists of an address match plus a count, both of which are specified as parameters in
      the RTT command. Alternatively, a logic 0 on user probe 5 substitutes for the address match portion of the
      trigger qualification.
      «option»        This optional parameter defines which types of bus cycles are to be stored in the trace buffer.
                      It may be specified by one of the following values:
                      option            transactions
                      F                 Instruction Fetches Only
                      I                 I/O Accesses Only
                      M                 Memory Accesses Only
                      R                 Read Operations Only
                      W                 Write Operations Only
                      IR                I/O Reads Only
                      IW                I/O Writes Only.
                      MR                Memory Reads Only.
                      MW                Memory Writes Only
                      *                 All Bus Transactions (Default)
                      OFF               Disarm Real-Time Trace
     2.2 System commands                                                                                            19


     «address»      This optional parameter may be any hexadecimal address in the range h'0000'-h'ffff'. Entering
                    a valid «address» will arm the "stop on address-compare plus count". If «address» is not
                    entered, the "stop" feature will be disarmed and the final 256 instructions executed are stored.
                    If «address» is entered, «option» must be entered or placeheld with 2 commas.
     «count»        This optional parameter may be entered only if «address» is entered also. If «address» is
                    entered with no «count», the «count» will default to 128.
     Usage notes:
        1. The Real-Time Trace, when armed, continually stores the requested transaction type in its circular
             buffer as a user program executes. If at least 256 transactions are stored, they will be the last 256
             transactions which occurred before the job terminated.
        2. The contents of the Real-Time Trace buffer may be displayed by using the "Display Real-Time
             Trace" command, DRT.
         3.   Note that the "stop" feature allows a snap-shot of transactions to be saved which describes real-time
              events before and after a given address is encountered.
         4.   Whether or not the "stop" feature is used, the user program continues its execution to completion.
              That is, the stop only stops storage of transactions in the Real-Time Trace buffer, not of user
              program execution.
         5.   If the Real-Time Trace is armed and the Debug trace is running simultaneously, the internal branch
              instructions for halting/restarting the slave during Debug trace will be stored in the Real-Time
              Trace' buffer.

        commands and "binary"-commands are possible. The commands to use are determined by "ANDing" the
        bits 0 – 3 of the types of the devices. If "binary"-commands are allowed (bit 1 is a 1), then the commands
        "read binary" and "write binary" are used with a block length of 128. In all other cases the commands "read
        ASCII" and "write ASCII" are employed.
        If multiple input files are specified with COPY, their contents are concatenated into the output file.
        PRINT uses the same options as PRINTL (see 2.4.8).
        (SDOS4+ only) If the output of COPY is CONO, then the console output can be interrupted with Escape.

2.4.3   DELETE
                 DELETE «filename/d» [«filename/d»]
        This command deletes all the filenames specified in its parameter list. Each filename must have a drive
        number associated with it. Each file specified in the parameter list will be deleted from the directory of the
        disk on which it resides, and the sector blocks allocated to the file will be released for reallocation.

2.4.4   DFIL and DFILE
                 DFIL «filename» («outputdev») («start») («end»)                           (SDOS3 only)
                 DFILE «filename» («outputdev») («start») («end»)                          (SDOS4 only)
        The DFIL command is used to dump a file in hexadecimal format to the specified device. If an output device
        is not named, the file dump is listed on CONO.
        For readability, the output is formatted in blocks of 128 bytes of data, sixteen data bytes per line. ASCII
        interpretation of the hexadecimal data is printed to the right of each data line. Bytes which are not ASCII
        characters are interpreted as a period.
        The file is dumped according to the following rules.
             1. The file is dumped from beginning of file if «start» is not specified.
             2. The file is dumped to end-of-file, if «end» is not specified.
             3. «start» byte and «end» byte must be valid Hexadecimal numbers in the range h’0000’ through
                  h’ffff’.
             4. «start» must be less than or equal to «end».
             5. If «start» equals «end» only one byte is output.
             6. If «end» byte is greater than the file size, the dump continues until an end-of-file is reached.

2.4.5   DUP
        The DUP command causes an exact duplication of the contents of the diskette in
        drive 1 to be created on the diskette in drive 2.
                 DUP «drive1» «drive2» («identity»)
        2.4 Diskette and file utilities                                                                                 25


        The DUP command causes the files and directory data stored on the diskette on disk drive «drive1» to be
        copied onto the diskette on disk drive «drive2». The disk drive number entered for «drive1» may not be
        the same as the number used for «drive2». In addition, the number used for «drive2» may not specify the
        system drive.
        The «identity» portion of the command is optional but serves to identify the new diskette. This
        identification is always displayed when the disk directory is listed. If the «identity» is not specified at the
        time of formatting, a string of blanks is used to identify the new diskette. The «identity» is truncated to
        48 characters if more than that are entered.
        If a disk read or write error occurs during a file copy, the output file is deleted from the flexible disk on drive
        «drive2», a warning message is displayed on the system console, and the DUP process continues with the
        next file. The diskette on drive «drive2» should be verified before the DUP command is executed in order
        to establish the bad block bit map for the diskette.
        Uses for the DUP command include making backup diskettes for your system. At times you may want to
        make a backup diskette for a non-system diskette. If your system has more than two disk drives, the DUP
        command can be used if you have the system disk in the system drive and the other two flexible disks in
        other drives. The system disk is needed to provide the DUP command.
        1f you have the minimum system with only two disk drives, it might seem impossible to DUP a non-system
        diskette. The following procedure allows you to use your system to duplicate non-system diskettes.
            1. Insert the system disk into drive 0 and toggle the Reset switch.
             2.   After the prompt character is displayed on the console, enter the following command:
                  DUP 1 0
             3.   An error message will be displayed along with an End-Of-Job message, because drive «drive2»
                  cannot be the system drive. However, the DUP command is now resident in system memory and the
                  system diskette is not required for execution of the DUP command.
             4.   Insert the non-system diskette to be copied into disk drive 1.
             5.   Remove the system diskette from drive 0 and insert a blank diskette into drive 0.
             6.   Enter the following commands
                  SYSTEM 1
                  DUP 1 0
        The files on the diskette in drive 1 will now be copied onto the blank diskette drive 0.

2.4.6   FORMAT
                  FORMAT «d» («ident»)
        This command causes the diskette on drive «d» to be formatted. The ASCII character string «ident» is
        used to identify the diskette. «ident» is truncated if it is longer than 48 characters.
        EXOS and SDOS3+: «d» may not be the designated system drive.
        The formatting process is primarily performed by the floppy disk controller and involves writing clock bits,
        sync patterns, the track and sector number, a data pattern and a CRC character on every sector of the
        diskette. During the formatting process, the directory is preset to indicate that tracks 1 through 4 are in use.
        This serves to reserve those tracks for DOS. If a bad sector is detected on tracks 0 through 4 (the directory
        and DOS area) the formatting process is aborted.

         Note: The filename used for the reservation depends on the OS version. Variants seen on the disk images
                so far include UDOS, SDOS, TOS, EXOS, and TEKDOS. The FORMAT command will create this file
                and reserve the first sixteen blocks, but does not write its contents. To actually make a diskette
                bootable use the COPYSYS procedure. This will copy DOS and its modules as well as supplied
                procedures.

        If the diskette will not be used for storage of system software, the area reserved for DOS may be freed for
        use by use of the DELETE command. This, however, will prevent ever using this diskette as a system disk.
        When the formatting process is completed, the ASCII character string «ident» is written to the diskette and
        serves as the diskette identification. This identification is displayed when the LDIR command is used to list
        26                                                                                      Diskette and file utilities 2.4


        the diskette directory. Note that if «ident» is not specified, a string of blanks will be used to identify the
        diskette.
        Virgin diskettes must be formatted and verified before they can be used by DOS.
        SDOS4: FORMAT will reenable the interval timer interrupt if it was disabled.

2.4.7   LDIR
        The LDIR command causes the contents of a floppy disk directory to be sent to the specified device.
                 LDIR («d») ( . ) ( / ) («device»)
        The LDIR command lists the contents of the disk directory that is mounted on the specified disk drive. If the
        disk drive is not specified, the system disk directory is listed. When a decimal point "." is specified as a
        parameter, all DOS system files will be included in the directory listing. When a slash "/" is specified as one
        of the parameters, space allocation information and file identification information are included in the listing.
        Any valid file may be named as an output device; however, you must specify the disk drive where the
        flexible disk with that file is located. The listing of the directory to a file will overlay any data in that file. A
        new file will be created if a file with the specified name does not exist.
        The diskette identification precedes the directory listing.
        All except SDOS1: A summary of diskette sector usage follows the directory listing. The SDOS system file
        sector usage is included in the summary, whether or not the "." option was specified.
        SDOS4+ only: If the output device is a file then a drive number must be specified.

         Note: The slash requires each file to be inspected, to see whether it is a module and if so to display its
                identity information. This requires a lot of disk drive head movement, and is quite slow.

2.4.8   PRINTL
                 PRINTL «filename» («output») («L1» («L2»))
        This command causes lines from «filename» to be written to a specified output device. If «output» is not
        specified, the data is printed on LPT1. If «L1» and «L2» are specified, they must be greater than or equal to
        1 and less than 32,768. «L2» must be greater than or equal to «L1».
        If a line range is specified (both «L1» and «L2»), only the lines from «L1» through «L2» will be printed. If
        only «L1» is specified, the lines from the first line through «L1» will be printed. If no line range is
        specified, the entire file will be printed.
        If PRINTL is used, the lines will be numbered and (SDOS1 excepted) a form feed will be inserted every 61
        lines printed.
        If PRINT is used the lines will be unnumbered and no form feeds are used.

2.4.9   PRH
        (TOS+ only) The command PRH can be used to print the contents of a file in hexadecimal characters. The
        format of the command is:
                 PRH «file» («device»)
        The first operand specifies the file from which the data are to be taken. The second operand designates the
        output device. Its default value is LPT1.
        The command produces 2 output lines for every 32 bytes of data (16 bytes if «device» is CONO). The first
        line contains the ASCII characters associated to the data bytes and the second line gives the values in
        hexadecimal notation.
        SDOS offers an equivalent; see DFIL and DFILE, 2.4.4.

2.4.10 PUNCH
        (EXOS only) The command PUNCH can be used to punch a readable text in papertape. The format of the
        command is:
                 PUNCH «data»
      2.4 Diskette and file utilities                                                                             27


      In which «data» represents the character string to punch. «data» may contain any ASCII character that is
      represented by a code in the range h'20' – h'5F'.
      Each character is replaced by a string of 6 bytes (giving the original character in a readable form) and these
      strings are punched in papertape.

       Note: The system command line processor considers «data» as a string of parameters. This results in the
              replacement of a comma by a space and a number of consecutive spaces are replaced by a single
              space.

2.4.11 RENAME
                RENAME «oldfile/d» «newfile»
                RENAME «d» «identity»
      The RENAME function has two forms. The first form renames the file «oldfile» to «newfile». This form
      requires that a drive number be specified with «oldfile». If a drive number is specified with «newfile»,
      it must be the same as the drive number specified with «oldfile».
      The second form reidentifies the diskette on drive «d» with the character string «identity»; it will be
      truncated if it is longer than 48 characters.

2.4.12 VERIFY
                VERIFY («d»)                   (SDOS1 only)
                VERIFY «d»
      This command causes the diskette on drive «d» to be verified.
      The verification process consists of reading every sector on the diskette and noting all the errors that occur.
      If an error occurs when a sector is read, bits corresponding to all the logical blocks on the track which
      contains the bad sector are set in a Bad Block Bit Map. In addition, the track and sector number of the
      defective sector are output to the console. Note that all four blocks on the affected track will be marked as
      bad, not just the block in which the error occurred.
      When all the sectors have been read, the Bad Block Bit Map is written on the diskette. Whenever files are
      created and disk space allocation for the file is performed, reference will be made to the Bad Block Bit Map
      and the defective blocks will not be allocated.
      If a defective sector is detected on any of tracks 0 through 4 (the DOS system area) during the verification
      process, the process will be aborted and an appropriate message will be displayed on the console. Note that
      even if a diskette is not used as a boot disk, errors in the DOS storage area are still fatal.

2.5.2   CSMS, RSMS, and WSMS
        Read, write and compare files in SMS paper tape format against slave memory. See Annex D of the SDOS
        Reference Manual for a description of the SMS format. SMS format was used by Signetics for the
        generation of PROMs.
                 CSMS («address» («device»))
                 RSMS («address» («device»))
                 WSMS («address» («device»))

        with the SMS file. The default value of «address» is 0. «device» is the input device or disk file where the
        SMS data is present. The default value of «device» is TTYR. CONI cannot be the input device.

        location are not equal, the memory location, the SMS value, and the contents of the memory location will be

        RSMS ….

2.5.3   DUMP, EXAM, EX and PATCH
                 DUMP «start-address» «end-address» («device»)
                 EXAM «address»
                 PATCH «address» «hexstring»      (except TOS+)
        The command DUMP may be used to display the contents of the memory. The start address is rounded down
        to the nearest multiple of 16, and the end address is rounded up to the nearest multiple of 16 minus one.
        DUMP therefore always prints a full line of 16 hex values, from address xxx0 to xxxf. SDOS3+/4+: the
        ASCII representation of memory is printed as well.
        EXAM allows interactive inspection and modification of memory. After the initial memory byte is displayed,
        the user can press any of these keys to initiate the corresponding function:
                 Space: display the next sequential byte.
                 Linefeed or Delete (Rubout): Go to the next line and then display the current location and its
                           associated data byte.
                 Hex data pair: Replace the current memory location with the hex value. Then display the next
                           sequential byte.
                 Return: terminate the EXAM command.
        The display of memory bytes will automatically go to the next line and display the location and its data byte
        whenever the location to be displayed is a multiple of 16.
        EXOS only: The command is abbreviated to EX.
        PATCH allows the user to alter memory. address is a hexadecimal address constant. hexstring is a string
        of hexadecimal digits from 1 to 58 digits in length.
        The contents of slave memory starting at address is replaced with the value hexstring. This replacement
        is performed on a byte-to-byte basis. For example, PATCH 3000 3F001E would replace the data at location
        3000 in memory with 3F, the data at location 3001 with 00, and the data at location 3002 with 1E.


        All three commands can operate on the following memories:
        2.5 Object program utilities                                                                               29


            •    master memory;
            •    common memory;
            •    external user memory (SDOS3+ only).
        The master memory is selected if the address in the first operand is preceded (without any separation) by the
        character '*'. In other cases, either the common memory or the external user memory is involved.
        (EXOS and SDOS3+ only ??)
        The external user memory is accessed if the system is in full TWICE mode. In this case a little routine to
        access the external memory is placed in the common memory. The user shall reserve 135 bytes at the end of
        the first bank of the common memory for these routines. These routines are stored at the end of the first
        common memory bank, preceding the area that is reserved for the trace package (see DEBUG). The user
        cannot specify another load-address for these routines.

         (EXOS only) Note: The programs for the command EXAM and DUMP differ for a 2650 slave and a Z80
               slave. This difference is significant only in the full TWICE mode.

2.5.7   MODULE

        then a module is created that loads into that respective overlay area, to be executed by the master processor.

2.6.1   ACCNT
        TOS+ only: The command ACCNT can be used to retrieve the accumulated execution time of traced
        instructions. The execution times are determined only with the 2650 slave.
        2.6 Debug commands                                                                                          31


        With each instruction trace the execution time of the traced instruction (expressed in machine cycles) is
        computed. These execution times are accumulated. The accumulated execution time is displayed by the
        command ACCNT. After the display the accumulator is cleared.
        EXOS only: With the Z80 slave always the value 0 is returned.

2.6.2   BKPT and CLBP
                 BKPT «address» (READ)
                 BKPT «address» (WRITE)
                 BKPT «address» («count») (READ)                                 SDOS 4.2 only
                 BKPT «address» («count») (WRITE)                                SDOS 4.2 only
                 CLBP («address»)
        BKPT causes a program breakpoint to be set for the slave. Breakpoints can be set on instructions or on data
        storage. If WRITE is specified the break occurs only when there is an attempt to write to the specified
        address. If READ is specified, the break occurs only when the instruction at that address is executing or when
        there is an attempt to read the specified address. If neither WRITE nor READ are specified the break occurs
        whenever there is an attempt to read or write to the specified address, or to execute the instruction.
        SDOS 4.2+: The optional «count» (specified as a normal decimal number) causes the breakpoint to
        "activate" only once every «count» times. Each time the breakpoint is triggered its counter is decremented,
        but execution is paused and the trace line shown only when the counter hits zero.
        The BKPT command can be used to change the trigger conditions (read/execute, write or both) of an existing
        breakpoint address.
        When the breakpoint address is accessed (read, written or executed) during program execution, a trace line is
        displayed on the debug output device, and a breakpoint message is displayed at the console.
        Up to two breakpoints may be active in the system. The number of breakpoints is limited because they are
        monitored and triggered at the hardware level by the Debug card.

         Note: the command BKPT 1234 RW will only set a Read-breakpoint, not a Write-breakpoint, because
                 only the first letter of the argument is inspected. If you want to set a breakpoint for both Read and
                 Write, then omit the parameter.

        CLBP clears a breakpoint. If «address» is specified, the breakpoint at the specified address is cleared. If no
        «address» is specified, all (both) breakpoints are cleared.

2.6.6   SET
        This command can be executed only when the corresponding slave CPU is active. Also, the format of the

                 SET PSU «D1» ( «D2» )

        other version to set the program status word. SET PSU «D1» causes the PSU of the slave CPU to be set to
        «D1». Set PSU D1 D2 causes the PSU to be set to «D1» and the PSL to be set to «D2». SET PSL «D»

        registers for which a value is given are changed. «value1» is assigned to the specified register, «valuex» to

                  B C D E H L A F IX IY SP I R
        The limits for the registers B, C, D, E, H, L, A, I and R are h’00’ and h’ff’. The limits for the registers IX, IY
        and SP are h’0000’ and h’ffff’.

           3. DOS internals
        When no jobs are active DOS only responds to interrupt handlers for devices. The console device handler
        collects the characters entered by the operator. When the carriage return key is entered, the device handler
        will call the command handler. The command handler verifies that the command is present in the command
        table, looks up the corresponding module number, and loads that module into memory into its designated
        overlay area. If that area is still in use the command fails. Otherwise the corresponding job is activated, and
        presented to the dispatcher for scheduling. The dispatcher manages the control and execution of jobs. When
        the job is finished, the dispatcher clears up and marks the overlay as available again.
        The following sections describe these processes in more detail.



3.1     Jobs
        DOS has a rudimentary form of multitasking. At most four tasks (jobs) can be running simultaneously,
        although only one job can be active at any given time.
        Each job executes functions which have certain specific characteristics, including its location in memory.
        System commands always run as a fixed job. If another system command is already running and using the
        same job, that second command cannot be started. For example, the RENAME command always runs as job 2,
        and if another command is already running as job 2 then RENAME cannot run.
        Job 0:     Command line processing, loading of overlays, execution of procedures and signaling of errors. Job
                   0 refers to "DOS itself". DOS executes in Master memory (other than overlay areas 1 and 2).
        Job 1: Loaded into overlay area 1 (addresses h'1500' – h'187f' of the master memory). System commands
                   which may require a considerable amount of time to be executed. A special program to be executed
                   in this area is DEBUG. When DEBUG is active, other commands that require overlay 1 cannot be used.
                   Overlay area 2 can also be used by job 1, when the command is too large to fit in overlay area 1 and
                   overlay area 2 is free.
        Job 2: Loaded into overlay area 2 (addresses h'1880' – h'lbff' in the master memory). Low-priority system
                   commands, and commands which may also be executed when the system is in Debug-mode.
        Job 3: Job 3 is associated to all programs that are executed by a slave CPU. They are loaded into Common
                   Memory.
        Although some form of non-preemptive multitasking is possible jobs are not equivalent. Job 2 is a low-
        priority job. When the Esc-key is used on the console, the active job will be suspended but job 2 will be
        aborted.
        DOS can execute procedures, also called command files (similar to scripts, or batch files). A procedure is a
        text file in which each line contains a command line. Procedures are executed as job 0, but commands inside
        procedures are executed as job 1, 2 or 3.
        For more information on the control and administration of jobs see section 3.6.

3.1.1   Modules
        Most system commands are not performed directly by DOS, but are loaded from object code modules (see
        3.10) stored on the system diskette. These modules have filenames that start with the special character Ctrl-
        O (charModule). DOS contains tables CmdStrings and CommandVectors (see file CmdTable.2650) that
        relate system commands to module filenames. Each filename is restricted to a single letter (in addition to
        charModule).
        Several modules contain more than one system command. Each command starts at a (small) offset from the
        start of the module. For example the "4" module in SDOS2 holds the commands RESET, SET, BKPT and
        CLBP.
        38                                                                                                Jobs 3.1


        Some system commands do not fit into a single overlay area (e.g. LDIR or MODULE). These commands will
        start in overlay area 1 and immediately load an additional module into overlay area 2. They can then use the
        combined memory space of overlay areas 1 and 2. However, this is only possible if overlay area 2 is not in
        use. The extra module filename is not restricted to a single letter.
        Modules are loaded into their assigned overlay area; they cannot be loaded in a different area.
        DOS maintains information on which module is loaded in each overlay area. It avoids reloading a module
        from disk if that module that is already present in memory. For example, the first invocation of CLBP will
        load module "4"; a subsequent command BKPT will proceed without disk access. See the DUP command
        (section 2.4.5) for another example of why this is useful. This applies to DOS commands only; any
        additional modules that need to be loaded (most often because the command requires both overlay areas 1
        and 2) will be loaded again from disk.

3.1.2   Interaction with DOS
        Jobs interface with DOS in a number of ways.
            1. Any of the jobs 1, 2 and 3 can execute a list of functions which are located in the resident DOS
                 area, through a Supervisor call. Supervisor calls are described in Chapter 3.11.
            2. For jobs 1 and 2 (the system commands) only, DOS also provides an API to commonly used
                 routines. These are stored at fixed addresses starting at h’2000’, regardless of the OS version,
                 thereby guaranteeing a stable API. These are described in Chapter 5.
            3. In addition, jobs 1 and 2 can directly access internal DOS variables, often only to inspect the
                 current state. The KILL and TYPE commands, for example, directly modify internal DOS flags.
        When job 1 or 2 terminates, DOS will report on the error reported through the API error function
        API_QueueErrorR0R1, if any.




3.2     Memory
        The memory of the TWIN is partitioned in two main parts:
        Master memory
                The master memory (16 kB) contains the locations with addresses h'0000' – h'3FFF'. Only the
                master CPU has access to this part of the memory. A misbehaving slave cannot accidentally
                overwrite this memory. This was a main selling point of the TWIN.
        Common memory
              The common memory can be accessed by both the master CPU and the slave CPU. It can contain
              up to 64 k (k = 1024) bytes. The slave CPU uses the addresses h'0000' – h'FFFF' to address this
              memory. Using the SLAVE command, the slave can be restricted to a particular portion of common
              memory. Theoretically this can be used to allow two slave CPUs to coexist, each in their own and
              protected part of common memory.
              For the master CPU this memory consists up to 4 memory banks of 16 kB each. The master CPU
              can select one bank at a time. It uses the addresses h'4000' – h'7FFF' for the selected bank.

3.3   DOS source code architecture
      The OS is partitioned into a number of components, each with their own function.
      Command line processing
              The command line processor CommandProc.2650 deals with the system commands which are
              entered via the console input or which are read from a procedure file.
              The command line processing comprises the determination of the specified system commands,
              loading of the associated programs and initialization of the related jobs.
      Supervisor calls (SVC)
              Many standard operations (such as input/output) are controlled via SVC's. A SVC is identified by a
              SRB (service request block). A SRB describes the requested operation and it will contain the
              termination status. Any job can issue SVC's, even though the invocation method is different for
              slave jobs. The DOS component Supervisor.2650 controls SVCs, and delegates processing to
              the appropriate device driver for I/O operations.
      File management
              All input/output operations are related to abstract channels. Upon the initiation of input/output a
              channel is mapped into a particular disk file or peripheral device. This approach frees the user from
              most peripheral characteristics.
              The file management programs are a part of the SVC-programs as well as a part of the device
              handling programs.
              The File Control Block (FCB, see section 3.8) holds all bookkeeping data on the current state of
              files and channels.
      Device handlers
              A device handler corresponds to a particular peripheral device. The system includes device handlers
              for:
              ◦ Line printer;
              ◦ Floppy disks (sector disks);
              ◦ Teletype and console;
      40                                                                            DOS source code architecture 3.3


               ◦   Serial ports;
               ◦   Papertape equipment.
               The Device Control Block (DCB.2650, see section 3.7) holds all bookkeeping data on the current
               state of devices. In addition, the Disk Control Block ( DskCB.2650, see section 3.9) holds
               bookkeeping data on the current state of inserted diskettes.
      Dispatcher
              The dispatcher (DOS component Dispatch.2650) is responsible for the selection of the next
              function to be executed. It acts as a (non-preemptive) scheduler of jobs. The dispatcher
              distinguishes the following classes of functions:
              ◦ Device handlers;
              ◦ Job 0;
              ◦ Job 1, job 2 and job 3;
              ◦ Procedure.
               The Job Control Block (JCB.2650, see section 3.6) holds all bookkeeping data on the current state
               of jobs.



3.4   Files and devices
      The TWIN Operating system is a file-oriented system. With the file management the concepts of "file",
      "device" and "channel" are used.
      A file is a set of data. A file can be processed sequentially only; processing always starts with the first data
      item and it is terminated with the last data item. Random access is not possible. In the TWIN system files are
      stored on floppy disks (diskettes). A disk file is identified by its name: the file name.
      Devices are physical peripherals which provide for input/output services. There are also pseudo devices
      which are not physical, but appear to DOS as physical devices. The TWIN system can contain up to 16
      devices. The standard devices have reserved names through which the user can access them. These names
      cannot be employed for file names. The reserved names with the associated peripheral devices are as

3.5     Diskette layout
        A diskette contains 77 tracks on which data can be written and from which data can be read. Each track
        contains 32 sectors; 128 bytes of data can be stored in a sector. Diskettes are single sided, and the disk
        controller requires hard-sectored diskettes.
        The first track, track 0, is reserved for directory data.
              • Sector 0: Disk Identity Block (DIB), one sector.
              • Sector 1 to 5: File Name Blocks (FNB), 5 sectors.
              • Sector 6 to 31: File Info Blocks (FIB), 26 sectors.
        The directory has space to hold 78 files at maximum.
        Tracks 1 to 76 are used to store file data. Space is allocated in multiples of blocks. A block comprises 8
        sectors. Each track is logically partitioned into 4 blocks, and a diskette can contain 304 blocks.
        Information on blocks can be stored in a block bitmap. For 304 blocks exactly 38 bytes are required. The
        first byte covers blocks 0 to 7, etc. The lowest bit corresponds to the lowest block number. There are bitmaps
        for used blocks on a diskette, to identify bad blocks on a disk, and to mark the blocks used for a file.

          Block bitmap layout

        directory information, named SDOS (or TOS, EXOS, etc). The FORMAT command will create this file and

                                  job should be scheduled for execution at first opportunity.
             3, jobstatExecuting: the job is currently running.

                                     again. The address of the next instruction is given by the I/O complete return
                                     address.
          6, jobstatSuspend:         the job has been suspended, most likely by the SUSPEND command.
                                     JobPrevStatus contains the job state before being suspended.
          7, jobstatAbort:       the job has indicated that it can be terminated. Any open channels should be
                                 closed, after which the job will be idle.
         8, jobstatPause:        the job has paused itself. Its overlay area is still occupied, but the job will not
                                 be restarted unless some other job changes job status. This state can for
                                 example be used to reserve overlay area 2 for system commands that require
                                 both areas 1 and 2.
      JobPrevStatus: previous state of the job, before it was suspended. When the job is continued – most
         likely by the CONT command – it will return to this job status.
      JobChanAssigned: a bit mask for channels 0 to 7. A bit 1 indicates that that channel has been assigned.
      JobChanActive: a bit mask for channels 0 to 7. A bit 1 indicates that that channel has an active Supervisor
          call.
      JobWaitingForCh: a bit mask for channels 0..7. A bit 1 indicates that the channel prevents the job from
         being scheduled for execution, because of an active Supervisor call. If the flag srbFnNoWait was used
          in a Supervisor calls to indicate that execution of the job should continue immediately after placing the
          call then the channel will be marked in JobChanActive but not in JobWaitingForCh.
      JobChanIOComplete: a bit mask for channels 0..7. A bit 1 indicates that the Supervisor call for that
          channel has been completed.
      JobWait: if non-zero, the job number for which this job is waiting. When the indicated job has finished,
         execution of this job should continue at JobWaitReturnAdr.
      JobCmdvecIdx: indicates the command that the job is currently executing. Values are indices into the table
         CommandVectors (see file CmdTable.2650).
      JobBank: bank to use when transferring data to/from the (slave) job, or when returning control to the job at
         some return address.
      ModuleStartOffset: offset of the starting address within the module. Normally zero, but can be non-zero
         when the module file for a system command contains more than one command.
      ModuleStartAdr: The start address for execution. Is obtained from the header of the module file or (for
         slave jobs) from the GO command.
      SRBreturnAdr: Return address specified in the Service Request Block SRB
      JobWaitReturnAdr: Continuation address after waiting for another job (in JobWait) to finish (in a
          procedure, or because of Supervisor call srbFnExecOvl).

3.10 Module files
      Modules contain executable code that can be loaded into master or slave memory. Almost all DOS
      commands are provided as modules. DOS’ module files are stored in hidden files: the first character of the
      filename is Ctrl-O (h'0F'). Note that LDIR can show hidden files on a disk when using “LDIR .” .
      Modules consists of a 128-byte (one sector) header, followed by data bytes. Most often the data bytes are
      consecutively stored at the starting address, but the actual load sequence is dictated by load commands listed
      in the header. See the table below; offsets are hexadecimal, lengths are decimal.
      Offset         Length        Meaning
      00..02         3             "MOD"
      03             1             01=overlay area 1, 02=overlay area 2, 03=slave memory
      04..05         2             Load address (slave's perspective)
     3.10 Module files                                                                                             45


     Offset         Length        Meaning
     06..07         2             End address
     08..09         2             Start address (first address of execution)
     0a..1f         22            Identity (e.g. module name, version, date), 0d terminated text.
     20..7f         var           Load commands (variable length)
     From offset h'20' onwards there are one or more load commands. Load commands start with a command
     byte, followed by one or two bytes, depending on the command. In the explanation below the command byte
     is separated into its eight bits (0 or 1, a letter indicating a special function, or ‘x’ for don’t care).
     Set Base: bbxx-x00x
           bb is the bank. The two bytes following this command byte indicate the base address from the master’s
           perspective. This base address is used for the subsequent Read Data command.
     Read Data: abcd-e010
           000a bcde is the number of sectors to read, minus 1. The byte following this command byte is the
           length for each of these read operations. Typically this length is h'80' (128) for one full sector, but
           when the number of sectors is one (the first or last sector to be read), the length will often be less than
           128.
     Load End: xxxx-x10x
           Indicates the end of the list of load commands.
     The DOS overlay areas are small, just under 900 bytes each. Some DOS commands actually consist of two
     modules. The LDIR command for example, in module file “Ctrl-O L”, is loaded into overlay area 1. LDIR
     then verifies that overlay area 2 is not in use, and loads module file “Ctrl-O O” into overlay area 2.
     Code that is too large for overlay areas 1 and 2 combined has to be loaded into slave memory, and then has
     to be executed by the slave processor. The ASM command for example is executed as a slave job. This also
     means that the corresponding slave card has to be present in the system.



3.11 Security
     This section can be brief, because the TWIN security model is mostly absent. Access to the machine is
     controlled physically by a key. There is no concept of signing on, password protection or any other access
     control.
     The only built-in limitation is that certain Supervisor functions are restricted to DOS modules (those running
     as job 1 or 2, or those running on the slave processor as job 3 provided that their filename starts with the
     special character Ctrl-O).

         4. Supervisor calls
      A program which wants to perform a system function (such as an input/output operation) can request the
      execution of such a function by means of a "supervisor call" or "service call" (SVC). All the data required to
      perform the requested function are contained in a Service Request Block (SRB).



4.1   Calling the Supervisor
      For Master jobs, the address of the SRB is is passed to the SVC processor with the supervisor call, using the
      register pair R2-R3 of the current register bank. Call the Supervisor by a straight branch (not a subroutine
      branch) to API_SupervisorCall. The program resumes at the set address. On return the following is true:
           • R0 contains the channel (for SVCs that performed channel I/O)
           • R0 contains the job status (when a job is resumed otherwise)
      For Slave jobs, the another mechanism must be used. They must force the master processor out of its Halt
      state using an interrupt, for it to be able to execute SVCs. The Debug card in the TWIN generates a SVC
      interrupt when the slave CPU executes an I/O instruction (either "write" or "read") to one of the I/O-ports
      h'F7' – h'F2'. The Millennium Operator Reference Manual says that the I/O instruction should be followed
      by a NOP-instruction, but this appears to be unnecessary.
      The addressed I/O-port designates the locations in the slave memory at which a pointer to the SRB is stored:

      I/O-port                                   SRB pointer location
      ioPort_SVC1, h'F7'                         h'0040'
      ioPort_SVC2, h'F6'                         h'0042'
      ioPort_SVC3, h'F5'                         h'0044'
      ioPort_SVC4, h'F4'                         h'0046'
      ioPort_SVC5, h'F3'                         h'0048'
      ioPort_SVC6, h'F2'                         h'004A'

      Check: will this also work in slave mode 1 and 2, or are these ports then only mapped to the prototype? The
      Tektronix manual claims it only works in mode 0. Perhaps this is done in software, by disabling bit-flag 10
      in the Debug Command register ?
      The I/O-ports with addresses ioPort_SVClodreg (h'F0') and ioPort_SVCsavreg (h'F1') are also used to
      interrupt the master CPU, but are not used for SVCs (see chapter 8).

A SRB shall not cross an 8 k boundary. The meaning of the components is:
srbFunc – SVC function code
       The SVC function code specifies the requested function. The top three bits of the function code are
       used as modifiers:
         srbFnBinary: read or write raw binary strings, instead of processed ASCII strings.
         srbFnBlock: read or write in blocks of 128 bytes, instead of strings of bytes. This only applies to
         disk files; 'real' devices treat this the same as srbFnBinary.
         srbFnSpecial: variants with function-specific meaning.
         srbFnNoWait: return immediately to the caller, instead of waiting for the I/O to complete before
         continuing.

 Note: Not all modifiers are possible with all functions. DOS contains a fixed list of all permissible
       functions and modifiers (in file SVCfnTable.2650). Combinations not in this list will cause an
       error. The allowed function codes are given in the following sections.

         All SRBs must contain a function code.
srbChan – channel number
         A channel number, in the range h'00' – h'07', is required for all I/O functions. It is not significant
         with other functions. The channel number is set by the caller.
srbStatus – result status
         The status reflects the state of the requested function. It is set by the SVC processor. The possible
         status conditions depend on the requested function and they are listed with the description of the
         functions.
srbData – single byte data
         This byte can be used to pass a single byte data item between the caller and the SVC processor. Its
         usage depends on the requested function. After the termination of I/O operations it contains the
         status of the peripheral device.
srbCount – buffer byte count
         With Read and Write functions this count denotes the number of data bytes which have been moved
      4.2 SRB structure                                                                                            49


               between the input/output area and the device. It is also used in conjunction with srbData to return
               2 byte data requested by non-I/O functions. The information in this byte is always supplied by the
               SVC processor.
      srbBMax – buffer maximum size
               A binary number denoting the length of the buffer, expressed in the number of occupied bytes. The
               buffer length is supplied by the caller.
      srbBufPtr – buffer pointer
               The address of the buffer. The buffer is the input/output area with Read and Write functions. If
               applicable, it is the address of the involved data string with non-I/O functions. The buffer pointer is
               to be set by the caller. The buffer shall not cross an 8 k boundary.
      srbRet – master SVC complete return address
               The address of the instruction that is to be executed next when the caller is continued.
             This component is relevant only for SVC's that are issued by programs being executed by the
             master CPU. The return address is supplied by the caller.
             SVC’s issued by programs running on the slave CPU continue at the instruction immediately after
             the read or write to the SVC I/O port.
      srbDirIO – pointer to direct disk I/O command string
             The address of the command string that is to be used with the SVC srbFnDirectIO. This is a
             privileged function. The address is to be set by the user. This field can be omitted for all other
             functions.




4.3   Supervisor processing
      The SVC functions are partitioned into two categories: privileged functions and non-privileged functions.
      The privileged functions may only be requested by system programs; non-privileged functions may be
      requested by any program. A system program is program that is executed in the master CPU or (TOS+ only)
      a slave module with a name that starts with Ctrl-O ( charModule, h'0F'). (EXOS only) the Direct I/O
      function is always privileged, even for slave modules with a name that starts with Ctrl-O.
      The Supervisor checks the SVC function code against its table of permissible function codes (see file
      SVCfnTable.2650), and disallows privileged functions when appropriate. With I/O requests the given
      channel number is checked; it must be free for srbFnAssign and assigned within this job for all other I/O
      operations. Further execution is function dependent and is described in the following sections and/or in the
      chapter on Device drivers.
      General termination status:
               svcstatIllChan – Illegal Channel Number (other than 0...7)
               svcstatChanNA – Channel Not Assigned (for functions other than srbFnAssign)
               svcstatChanBusy – Channel Busy (for srbFnAssign)
               svcstatIllFn – Illegal Function Code (when the function is not listed or disallowed)

      EXOS only: The format of the pointers (both SRB pointer and buffer pointer) related to SVC's which are
      issued by the slave CPU depends on the endian-ness of the current slave CPU. With a 2650 slave, the first
      byte contains the bits 0 – 7 of the address and the second byte the bits 8 – 15. With a Z80 CPU, the contents
      of these bytes are exchanged (first byte bits 8 – 15 and second byte bits 0 – 7).


      The SVC functions are partitioned into the following groups:
          • input/output functions (4.4);
          • control functions (4.5);
          • miscellaneous functions (4.6).

   5. DOS API calls
Jobs 1 and 2 – the modules loaded into overlay areas 1 or 2 – can make use of a few routines and subroutines
that are exposed by all DOS versions in a version-independent manner. All DOS versions supply these
functions, and they are available at fixed addresses (h'2000' to h'201b').
Use either a normal jump to a routine or a subroutine call; the correct invocation is described in the sections
below.
         bsta,un       «API_function»                     use this for subroutines
         bcta,un       «API_function»                     use this for routines
This API has been stable in all known versions of DOS. It is therefore surprising that several modules for
DOS commands use their own routines for converting hexadecimal numbers to 16-bit values. Also, modules
often use indirection to call the API, as if the interface is subject to change. TOS improves upon this, using
the API more often and directly using the absolute API addresses. But the API appears to be poorly used,
especially when compared to the Supervisor Calls from the previous chapter.
The API contains routines that one would not expect to be used directly by user programs, such as those to
save and restore the register state. Some API routines have equivalent SVC functions, such as
API_SkipToJob12Pparam (srbFnParam) and API_Dispatcher (srbFnExit).

Out:           see SRB fields

Invoke as: subroutine at h'2003'
In:        none
Out:       none

API_IntRestrState
Restore register state, e.g. when finishing an interrupt handler.
Invoke as: subroutine at h'2006'
In:        none

API_ConvertASCtoNum
Convert a given ASCII string depicting a hexadecimal number into a binary value.
Invoke as: subroutine at h'2009'
In:        R2R3 = address of the given string

Conversion will fail when the number is too big, or contains invalid characters. Only hexadecimal characters
are allowed, at most 4 digits. The routine can be used to convert Binary Coded Decimal (BCD) numbers, if it
is checked separately that each digit is at most "9".
It is strange that many, if not most, of modules for system commands have their own subroutines for
converting addresses and number.

        Upon the assignment of the papertape punch to a channel, a string of 128 bytes h'00' (tape feed) is sent to the

6.3.2   WRITE
        With the execution of the command WRITE, the contents of the output area is sent to the papertape punch.
        The commands "write ASCII" and "write binary" are executed in a different way:
             1. Write ASCII
                  The most significant bit of each outgoing byte is used as parity bit. Its original value is ignored and
                  the new value is such that parity is even.
                  The output stream is terminated when either the control character CR has been transmitted or the
                  output area is exhausted.
             2. Write binary
                  All the bits in each outgoing byte are transmitted to the peripheral device without any modification.
                  The output stream is terminated only when all the data in the output area has been sent to the
                  peripheral.
        The device handler does not accept both types of write commands for the same file; all write commands are
        to be either "write ASCII" or "write binary".
        Termination status:
                  svcstatOK – FUNCTION COMPLETE
                  svcstatIllFn – ILLEGAL FUNCTION CODE
                  svcstatShortWr – NO EOL ON ASCII WRITE
                  svcstatDevNO – DEVICE NOT OPERATIONAL

        With an ASCII file (write commands "write ASCII"), the tape feed is preceded by the character CTRL-Z
        (h'lA' end-of-file). This character is not punched in binary files.
        After the completion of this transfer the punch motor is stopped and the device is released.
        Termination status:
                 svcstatOK – FUNCTION COMPLETE
                 svcstatDevNO – DEVICE NOT OPERATIONAL

                encountered. In both cases CR is stored as last character. When the input area is full, CR is stored in
                the location following the input area.
                The ASCII control characters are processed too (see 5).
            2. Read binary
                The input bytes are stored in the input area without any modification.
                The string is terminated only when the input area is full and no CR is added. Also no control
                characters are recognized.

6.5     Console
        The console handler consists of two closely related device handlers: the console input handler and the
        console output handler. The console input handler controls the console keyboard (or teletype reader), while
        the console output handler is responsible for the console display. They are closely related, because console
        input is typically echoed to console output.
        68                                                                                                 Console 6.5


6.5.1   Console input handler
        The console input handler recognizes only the command READ. With any other command the termination
        status svcstatOK (function complete) is returned. The console input handler distinguishes three types of
        read commands:
                 read ASCII;
                 read binary;
                 read ASCII without echo.
        With both "read ASCII" commands the ASCII control characters are processed as is described in section 3,
        but the control character ESC is processed further in order to detect consecutive ESC's (see 5.1.1).
        With the ordinary "read ASCII" command each entered character is passed to the console output handler to
        be echoed on the display. This does not occur with "read binary" and "read ASCII without echo".
        With both "read ASCII" commands the end of the input stream is detected when the input area is full or
        when the control character CR is found. In both cases CR is stored as last character. If the input area is full,
        CR is stored in the location following the input area.
        With "read binary" the end of the input stream is detected when the input area is full. Then no additional data
        are stored.
        Special read: with the ‘special’ option the input characters are not echoed to the terminal’s display. This
        could be used for password entry.
        Termination status:
                 svcstatOK – FUNCTION COMPLETE
                 svcstatShortRd – NO EOL ON ASCII READ
                 h'FF' – END OF FILE
        Because the console is the system control device, the console input handler deals also with entered
        characters when it is not involved in a read operation. Then only the control characters ESC and SP are
        accepted (see 5.1.1 and 5.1.2).

        6.5.2 Console output handler
        The console output handler recognizes the commands:
                write ASCII;
                write binary;
                reserve console (privileged);
                release console (privileged).
        With any other command the termination status svcstatOK (function complete) is returned.
        Again a distinction is made between "write ASCII" and "write binary".
             with "write ASCII" the byte h'0F' (CTRL-0) is replaced by A'.', the ASCII control character LF is
                substituted for the control character FF and, if the end of the string is found, the control characters
                CR and LF are sent to the peripheral display. With "write ASCII" the end of the string is attained
                when either the output area is exhausted or the control character CR is encountered.
             with "write binary" the byte h'0F' and the control character FF are not translated and, when the end
                of the string is found, no additional data are sent to the peripheral display. With "write binary" the
                end of the string is attained only when the output area is exhausted.
        Termination status:
                svcstatOK – FUNCTION COMPLETE
                svcstatShortWr – NO EOL ON ASCII WRITE
        The console output handler deals also with the console input data that are to be echoed. All characters are
        without any change translmitted to the peripheral display, except DEL, CR, FF and CTRL-0. These
        characters are replaced by the following data:
                 DEL: ESC – BS – SP – ESC – BS (erases character on screen)
                 CR:       CR -LF (positions cursor at beginning of next line)
                 FF:       LF (proceeds at next line)
                 CTRL-0:            A'.' (provides for a "printable" character)

6.6     Memory
        This is a pseudo-device, used to gain access to slave registers and memory regardless of ICE mode. It was
        most probably added in SDOS 3.0, and present in SDOS 4.0 and 4.2. It uses an expanded trace package: in
        addition to small routines to load and store the registers, the package also contains a small routine to copy
        memory contents between locations. This is used to either load or save register values from master or
        common memory, or to copy between master, common or user memory. The trace package is executed by
        the slave processor.
        If the Hardware Analyzer card is present then the trace package will be stored in common memory, and
        mapped into the slave processor's memory space for as long as the MEM device is active.
        The MEM device supports the following functions.

6.6.1   Assign and close
        Set the memory device as busy, but inactive.

6.6.2   Read
        Read (save) the current state of the slave registers. The register values are copied to the area pointed to by
        srbBufPtr; srbBMax should be less than 10 and the buffer area should be large enough to contain the
        requested number of register values.
        When srbFnBinary is used, the values are stored within DOS (in a storage area in the trace package) and
        srbBufPtr is not used.

6.6.3   Write
        Write (restore) the current state of the slave registers. The register values are taken from the area pointed to
        by srbBufPtr; srbBMax should be less than 10.
        When srbFnBinary is used, the values are taken from the storage area within DOS (in the trace package)
        and srbBufPtr is not used..

6.6.4   Special Direct I/O
        srbBufPtr points to a location containing 5 bytes the following structure:


             function        address A - hi       A - lo       address B - hi       B - lo


        The meaning of addresses A and B depend on the function:
        function              action                               address A                 address B
        0001 = 1              read slave mem,
        0010 = 2              used where?
        0011 = 3              copy between master addresses        source address            destination address
        0110 = 6              copy master to slave




6.7     GPIO serial port
        The serial port on the General Purpose I/O card is mostly handled by a single UART chip: the General
        Instruments AY-5-1012 (also available as Texas Instruments TMS-6011). The same UART chip as is used
        on some Master cards for the console interface, although other Master cards use the AY-5-1013.
        This UART chip does not provide hardware or software flow control. Flow control signals on the GPIO
        serial port are read and created using dedicated hardware on the GPIO card, separate from the UART. Even
        hardware flow control is therefore under software control, which severely limits its usefulness.

           8. Debugging
        Debugging with the TWIN requires a delicate interplay between hardware and software. A good
        understanding of hardware and software is necessary to understand how debugging works in detail.



8.1     Software perspective
        So far this section has been written based on TOS and SDOS2; SDOS4 is incomplete.
        SDOS2 loads the base debugging functions in overlay 1, to be executed as job 1. The DEBUG command sets
        this up. Other debugging system commands (such as DSTAT, BKPT or RESET) run in overlay 2 as job 2.
        These commands make use of generic functions that are enabled and provided by the DEBUG command. In
        order to “call” these functions, they pause themselves (job 2), schedule job 1 for execution at the desired
        module offset, and run the Dispatcher. The Dispatcher will then allow job 1 to run, which performs the
        desired function. On completion, it will pause itself (job 1) and schedule job 2 for execution, via the
        Dispatcher.
        During debugging SDOS2 will be switching between jobs 1 and 2. The interaction between these jobs is
        quite complex, and difficult to understand.
        TOS improves upon SDOS2 by putting all activity into job 1. Job 1 uses both overlay areas, but marks
        overlay area 2 as not in use when done, so that overlay 2 can be used by other system commands. This
        avoids the switching between job 1 and 2 via the Dispatcher; generic function provided by DEBUG can be
        used by straight branch or branch-to-subroutine instructions.

8.1.1   2650B
        Only SDOS4 can display the 2650B-only instructions LDPL and STPL. Other versions of DOS see these as
        invalid instructions.

8.1.2   Initializing debugging
        Until the DEBUG command is issued, none of the debugging commands are recognized by the command
        processor. File CmdTable.2650 contains the list of all DOS commands. This list contains a special mark,
        and commands after that mark are only recognized when bit h'20' of the Debug Control register has been set.
        As the I/O port (h'f8') for this register is write-only, DOS keeps a copy of that I/O port in memory.
        The DEBUG command loads module "D" into overlay area 1, and invokes the function DebugStart at offset
        3, as specified in CmdTable.2650. Routine DebugStart will then load module "2" into overlay area 2,
        which will set things up for debugging:
             • TOS only: announce the debugger and slave CPU.
                ** 2650 DEBUG **
            •   Set slave mode to 0. Check this, as this does not make sense.
            •   Set the values for TracePkgPushToSlave and TracePkgGetFromSlave. These DOS variables
                are used to make the slave jump to those locations, to load or store its registers, respectively.
            •   Set the values for DOS variables Registers and TracePkgBank, so that the master has access to
                the register copies. These values will be used by TracePkgPushToSlave and TracePkgGet-
                FromSlave.
            •   Store the trace package itself into the top-most page of slave memory (or at the address specified
                with the DEBUG command). Verify that the write was successful, or exit with MemWrite error. The
                trace package consists of the two routines mentioned above, and 9 data bytes holding the register
                values.
        74                                                                                       Software perspective 8.1


             •        Open channel 1 with CONO and (if specified with DEBUG) channel 2 with the destination device or
                      file. Store value 1 or 2 in DebugOutChan, so that tracing information can be written to the
                      destination (if necessary) and to the console.
             •        Enable debugging, and disable breakpoints and single-stepping by setting the appropriate bits of the
                      Debug Control register. Reset the slave through the Debug Command register. Enabling debugging
                      will also enable the debugging commands.
             •        TOS only: reset TimerTicks. SDOS does not enable timer interrupts.
             •  Change the entry point for DEBUG to offset +0 (effective h'1500') in ModuleStartOffset, so that
                unpausing job 1 will cause it to print one line of tracing information.
           • Finally, pause the DEBUG command. It remains loaded in memory, so that the (sub)routines that it
                provides remain available to DOS and other Debug commands. To end the debugging session use

             1. ShowTracingInfo: prints a TRACE line to CONO and (if specified) the debug output device.
                 2.    DBG_TestSCconditions: to test whether the current address and instruction match the filtering

        The Forced Jump Address register (I/O ports JumpAddrLo and ...hi) should contain inverted address
        values. In TOS, DOS variables TracePkgPushToSlave and TracePkgGetFromSlave contain inverted
        addresses. SDOS 2 stores plain addresses in the variables, which need to be inverted before writing to the
        I/O ports.

8.1.3   Trace package
        In order to read and set the current register values of the slave processor a small utility program is loaded
        into its memory: the trace package.
        SDOS 2 and TOS: The code for the trace package can be found in module "2" of DEBUG.
        SDOS4: The code for the trace package is kept in disk buffer DBUF1 in the SDOS file on the system
        diskette. Its contents are re-read by the UPR utility by directly accessing sector h'19' on track 2.
        To support the READ and WRITE commands a further utility program needs to be stored in slave memory.
        This utility will be stored just before the trace package.

8.1.4   Debug interrupt handling
        Interrupts 16 to 31 (h'10' to h'1f') are reserved for debugging; interrupts 16 to 21 are reserved for slave jobs,
        to interface with DOS. Interrupts 29, 30 and 31 are currently unassigned.
        When the master receives an interrupt, the handling differs somewhat for different DOS versions.

8.1.5   Interrupts in TOS
        Debug interrupt 16 to 21 – Slave SVC
        These interrupts are tied to interrupt handlers SlaveIntH1 to SlaveIntH6 in Supervisor.2650. The
        handler will fetch the SRB address, check whether the slave is executing a privileged module, then hand
        over to the SVC processor.

        Debug interrupt 22 – Service 1
        This interrupt is tied to interrupt handler DebugSVC1IntH in CoreIntH.2650. It is ignored unless
        expected, indicated by bit h'80' in DebugIntBits. Otherwise, its action depends on whether debugging is
        active:
        If debugging is active, sets job1 to job state Ready. This causes the Debug module to be run at module offset
        0, printing tracing information. After printing the trace line and if single-stepping the command prompt is
        displayed. If not single-stepping job3 is marked as Ready so that the slave will continue. With its next
        instruction.
        If debugging is not active, then set job2 to job state Ready. The purpose of this is to reactivate the DSTAT
        command after it requested ShowTracingInfo to print the slave CPU register state.
        8.1 Software perspective                                                                                   75


        This interrupt is solicited by a Forced Jump to TracePkgGetFromSlave. In the trace package the slave
        will save its register state, then write to I/O port ioPort_SVCsavreg, causing the interrupt.

        Debug interrupt 23 – Service 2
        This interrupt tied to interrupt handler DebugSVC2IntH in CoreIntH.2650. It is ignored unless expected,
        indicated by bit h'40' in DebugIntBits. Otherwise sets job3 to job state Paused.
        This interrupt is solicited by a Forced Jump to TracePkgPushToSlave. In the trace package the slave will
        restore its register state, then write to I/O port ioPort_SVClodreg, causing the interrupt.

        Debug interrupt 24 and 25 – Breakpoint
        These interrupts are tied to interrupt handlers BP1IntH/BP2IntH in CoreIntH.2650. They are ignored
        unless debugging is active.
        If debugging is active, the current value of the PCNext register and PCLast register are read and stored into
        DOS variables PCNextAddrFromSlave, PCNextAddrFromMaster/PCNextBank, PCLastFromSlave,
        and ModuleStartAdr for job3. The latter will be used by the Dispatcher to restart the slave. Then, a Forced
        Jump is performed (which was already initiated by the Debug card while raising the debug interrupt) to the
        TracePkgGetFromSlave routine. While preparing the Forced Jump, all debugging and tracing is disabled
        by clearing those flags in the Debug Control register. The Dispatcher is then allowed to run. When the
        Dispatcher schedules the slave, the trace package saves the slave CPU register state into Registers, then
        raises debug interrupt 22 (h'16') by writing to I/O port ioPort_SVCsavreg.
        The interrupt is solicited by activating either breakpoint in the Debug Control register.

        Debug interrupt 26 – Single-step
        This interrupt is tied to interrupt handler SingleCycleIntH in CoreIntH.2650. It is ignored unless
        debugging is active.
        When debugging, the current value of the PCNext register and PCLast are read and stored into DOS
        variables PCNextAddrFromSlave, PCNextAddrFromMaster/PCNextBank, PCLastFromSlave, and
        ModuleStartAdr for job3. Then calls routine DBG_TestSCconditions in the Debug module, to check
        whether all of the requested tracing conditions apply. If so, proceed as with Slave halted or Breakpoint
        above. If the conditions were not met, then allow the slave to continue by performing a Forced Jump to
        PCLastFromSlave.
        This interrupt is solicited by activating single-stepping in the Debug Control register.

        Debug interrupt 27 – Slave halted
        This interrupt is tied to interrupt handler SlaveHaltedIntH in CoreIntH.2650. If debugging is not
        active, DOS queues the Slave Halted error, and aborts job3.
        If debugging is active it performs the same actions as for Breakpoint interrupts.
        This interrupt is not explicitly solicited, but occurs when the slave executes the HALT instruction.

        Continuation after an interrupt
        After any interrupt handler finishes, the Dispatcher is allowed to run again, transferring control to whatever
        job is ready for performance. If any errors were queued, the Dispatcher will first display these on the
        console. If job3 is marked as ready and no other jobs need to be run, the Dispatcher executes a halt, thereby
        indicating to the Debug card that the slave can access the bus.

8.1.6   Interrupts in SDOS 2
        Interrupt handlers in SDOS 2 are a lot simpler than in TOS. They mostly set the appropriate flags, then exit.
        The Dispatcher will handle the follow-up, allowing job 1 (the DEBUG command in overlay area 1) to run and
        take appropriate action.

        Debug interrupt 16 to 21 – Slave SVC
        These interrupts are tied to interrupt handlers SlaveIntH1 to SlaveIntH6 in Supervisor.2650. The
        handler will fetch the SRB address, then hand over to the SVC processor. Only unprivileged SVCs can be
        executed.

        Debug interrupt 22 and 23 – Service 1 and 2
        These interrupts are tied to interrupt handlers DebugSVC1IntH/...SVC2IntH in CoreIntH.2650. They are

        Service interrupt 1 is solicited by a Forced Jump to TracePkgGetFromSlave. In the trace package the

8.2     Hardware perspective
        The Tektronix service manual has an excellent description of the hardware of the Debug card, including full
        circuit diagrams. Forced Jump logic is also implemented in part in the slave's hardware, but only a high-level
        description of the 2650 slave is available; see the Testware instrument System Reference.

8.2.1   Activating master or slave
        The Debug card enforces that at most one CPU is running and has access to the bus. The Debug card passes
        control over the bus from master to slave and vice versa by monitoring their halt state (the Run/Wait pin of
        the 2650 microprocessor) and by detecting special I/O events. Initially and after a reset the master CPU is
        active and running. The normal way for the master to cede control to the slave is the HALT instruction. For
        the slave the halt instruction indicates a programming error, and will cause a debug interrupt. Instead, writes
        to extended I/O ports h'f0' to h'f7' are used to transfer control back to the master.
        Note that an interrupt will wake the 2650 microprocessor out of its halted state. To prevent this hold the
        PAUSE input low (alternatively, hold or the RESET input high or stop the clock).
        The following conditions are monitored by the Debug card.
        8.2 Hardware perspective                                                                                         77


            •     When the master halts, the Debug card activates the slave CPU. The slave continues based on its
                  state before it was paused (a Forced Jump may be pending).
             • When the slave is running (and the master is therefore halted) and an I/O interrupt to the master
                  CPU is raised, the Debug card will pause the slave so that the master can respond to its interrupt.
             • When the slave goes from running to halted the Debug card raises interrupt 27 (h'1b') to the master.
             • When the slave writes to any of the extended I/O ports h'f0' to h'f7' the Debug card raises an
                  interrupt 23..16 (h'17'..h'10') respectively.
             • If debugging is active (bit h'20' of the Debug Control register is set), the Debug card will actively
                  compare the address bus for matches with either breakpoint register, including the corresponding
                  read or write direction on the data bus. If a match is detected on breakpoint 1 or 2, the Debug card
                  raises an interrupt 24 or 25 (h'18' or h'19') respectively.
             • If single-stepping is active (bit h'10' of the Debug Control register), the Debug card raises interrupt
                  26 (h'1a') at the start of each instruction fetch by the slave. It is up to the software interrupt handler
                  to decide whether to print trace information and/or continue. The function to trace only branch
                  instructions is implemented entirely in software. Single stepping will therefore significantly slow
                  down the slave, even when no tracing information is printed.
             • The Diagnostic Interrupt switch on the (standard) front panel raises interrupt 28 (h'1c'), regardless
                  of whether the master or slave was running.
        I/O ports h'f2' to h'f7' are allocated to SVC calls, but DOS is free to use h'f0' and h'f1' for any purpose. Many
        DOS versions use both, but SDOS4+ only uses h'f0'. Ports h'f0' and h'f1' are used in the Debug trace
        package, typically to save and restore the slave's register state.
        The Debug card also monitors many conditions on the full maintenance front panel. This hardware and
        circuit diagrams for the maintenance panel are lost.

8.2.2   Raising an interrupt
        When the Debug card raises an interrupt it pauses the slave, so that the bus can be used by the master. It
        activates the DBG INT signal, to wake the master CPU. On receipt of the DBG VEN signal from the master
        CPU card the Debug card places the corresponding interrupt vector on the data bus.
        When the slave is paused, it will do so after the fetch of the next instruction. The Debug card therefore
        initiates a Forced Jump when it pauses the slave, to that the slave fetches an absolute jump instruction
        instead of the normal next instruction. The slave then pauses. When the master gains control it can set the
        Forced Jump Address registers in its interrupt handler. By setting this register to the value obtained from the
        PCNextHi/Lo register the slave will continue (when it is scheduled to run) as if no interrupt occurred. The
        master can also point the Forced Jump Address register to the TracePkg-GetFromSlave routine, so that
        the slave will dump its register state; which the master can use to print TRACE information.

8.2.3   Forced Jump
        The Debug card contains a 16-bit write-only Forced Jump Address register (I/O ports JumpAddrHi/Lo),
        which can be written to by the master CPU. When set, writing a Forced Jump command to the Debug
        Command register will trigger the forced jump by raising the JMP CMD signal. When the Forced Jump
        logic on the slave card receives this signal, it will replace the contents of the next instruction fetch by an
        unconditional branch instruction. On the 2650 slave this is "bcta,un" or h'1f'. The next two memory fetches
        would normally obtain the destination address, but instead the Debug card puts the high and low bytes of the
        Forced Jump Address on the data bus.

8.2.4   Forced Reset
        When the master CPU writes a Forced Reset command to the Debug Command register, the Debug card
        activates the reset line to the slave CPU. The reset line is held active, and is only deactivated when the slave
        CPU becomes active.

8.2.5   Forced Interrupt
        When the master CPU writes a Forced Interrupt command to the Debug Command register, the Debug card
        briefly activates the interrupt line INT0 to the slave CPU.
        On the 2650 Slave card, INT0 will go to interrupt vector h'0000', which is also the starting address for Reset.
        The documentation says that Forced Interrupt is not used on the 2650 Slave card.

             9. Objects and linking
        The Signetics relocatable assembler produces output that is address-independent, meaning that assembled
        code can be adapted to run from any location in memory. Relocatable output contains the necessary
        information to perform this adaptation in addition to the actual code itself. Adaptation is done by the linker,
        which also combines multiple relocatable objects into a single executable. The output of the linker is a DOS
        module (see 3.10 "Module files").
        Relocatable objects may contain code, constants and data fields that are available for other objects to use.
        The names and labels of these items are exported by the object. In the relocatable assembler they are
        explicitly made available using the ENTRY directive.
        Relocatable objects may also require code, constants or data fields that are made available by other objects.
        The names and labels of these items are imported by the object. In the relocatable assembler they are
        explicitly declared using the EXTRN directive.



9.1     Relocation records
        Output of the relocatable assembler, and all input to the linker, consists of a sequence of records. If a file
        only contains Comment and Command records then the file is a plain text file. Files containing other kinds
        of objects will be binary files.
        The following record types are available:
            • CMT: comment records containing descriptive information
             •   CMD: command records containing instructions to the linker
             •   ESD: records containing external symbol definitions, describing the code, constants and data fields
                 that are either imported or exported by this object.
             •   RLD: relocation data, the information needed to adapt the next TXT-record.
             •   TXT: code (text) that may or may not have to be adapted, depending on whether it is preceded by an
                 RLD-record..
             •   END: record that terminates the object file.
        The first byte of each record is de record-ID, identifying the type of the record. Subsequent bytes and their
        number are dependent on the type of the record.

9.1.1   Comment records – CMT
         *              ASCII characters...                        «CR»
        Comments start with an asterisk in the left-most position of their line, and are terminated by a carriage
        return. Comments are ignored by the linker, but are copied verbatim into the listing file that is optionally
        produced by the linker (also called the load map).

9.1.2   Command records – COM
         (space)        ASCII characters...                        «CR»
        Commands start with a space in the left-most position of their line, and are terminated by a carriage return.
        Leading spaces in the command are ignored. There are two possible commands:
            • PHASE «filename» [,«origin»] [«module ID»]
                Describes an executable module as output; the term "phase" here means "executable output file".
                The module will be written to «filename», starting at «origin», with the given module ID.
        80                                                                                        Relocation records 9.1


                 If there is no PHASE command the name of the executable module must be supplied as a parameter
                 to the LINK command. If the optional origin is absent, the executable will be located at the address
                 specified in the first object file.
                 The optional module-ID must be separated from the filename or origin by a space, although some
                 documents (and linkers?) accept a comma as a valid parameter separator. Module-IDs can be at
                 most 21 characters in length.
             •   INCLUDE «filename»
                 Describes the name of an object file to use and include in the current output file. The included file
                 can contain INCLUDE commands itself. The DOS linker can handle nesting up to depth 4.
                 The filename must include a drive number if the file is not located on the system drive, unless the
                 SEARCH option is on (see 2.2.13).
        Command records can be inserted in binary objects produced by the relocatable assembler using the REPRO
        directive. The line after REPRO will be inserted verbatim as a command record to the linker.

9.1.3   External symbol definitions – ESD
        All ESD records must be at the start of the object module, before any RLD or TXT records.
         h'80' / h'81'   symbol (6 bytes)             type           value (2 bytes)       length (SD only)
        The symbol is the name of the reference (upper case, left aligned, padded with spaces). Type can be one of
        the following:
             • h'00': ER – external reference. The value indicates the sequence number of this reference, which is
                 used in subsequent RLD records. Although 16-bits are available for the sequence number, only 7-
                 bits are used (up to 128 external references per object file).
             • h'01': CD – constant definition. The value indicates the actual value of the constant. The constant
                 may be used in any of the four relocation types. In the assembler source for this object file the
                 constant will have been defined using the EQU directive.
             •   h'02': LD – label (entry) definition. The 15-bit value indicates the assembled address of the label.
                 The actual value may be different because the object file defining the label may be relocated. The
                 label may be used in any of the four relocation types.
             •   h'80': SD – section definition. The 15-bit value indicates the assembled starting address of the object
                 file. The actual starting address may be different, because of relocation. The 15-bit length (which
                 only occurs with section definitions) gives the number of code and data bytes in the object file. This
                 should equal the sum of the lengths of all TXT records.
                The section definition should be the first ESD record within the object file. The symbol refers to the
                label of the CSECT directive in the assembler source. If there is no CSECT directive in the source,
                the symbol will be empty (6 spaces).
        The record-ID must be h'80' for ER, CD and LD definitions; the record-ID must be h'81' for SD definitions.
        Symbol names must be unique; no two object files can export a symbol with the same name. Each symbol
        that is used in an RLD record must be declared in exactly one other object file for the phase. It is not an error
        if an exported symbol is not used by any other object file.
        The Pascal compiler and the accompanying linker use additional ESD types. For details see the compiler
        manual at https://ztpe.nl/2650/docs/2650-pascal/#compiler.

9.1.4   Relocation data – RLD
         h'01'           length        RLD instructions...

        The length indicates the number of bytes for the RLD instructions, not the number of instructions. Each RLD
        instruction is one, two or three bytes long:
        9.1 Relocation records                                                                                         81



                  7 6 5 4 3 2 1 0               sequence # (if external)     low byte value (if type 01)

                                                   1f offset within TXT record
                                                   20 0 = local, 1 = external (next byte gives sequence number)
                                                   c0 type: 00 low-order byte
                                                            01 high-order byte (next byte gives low-order value)
                                                            10 13-bit address
                                                            11 15-bit address
        When the type is 01 and external, the RLD instruction is three bytes long; the sequence number is given first
        followed by the low-order value. When the type is 01 and internal, the RLD instruction is two bytes long; the
        same applies to external instructions of type 00, 10 or 11. Internal instructions of type 00, 10 or 11 are one
        byte long.
        Each RLD-record modifies its subsequent TXT-record. The offset indicates the byte within the TXT-record
        that needs modification. Modification is always done by addition: a value is added to the value that is
        already present in the TXT-record.
        For internal RLD instructions the added value depends on the actual starting address of the object file. For
        external instructions the value depends the type of the exported symbol. For labels ( ESD LD records) both the
        value of the label and the actual starting address of the object file in which that label was defined will be
        added. For constants (ESD CD records) only its value will be added.
        Type 00 and 01 is used for immediate addressing. They correspond to the < and > operators in the
        assembler, that take the high-order or low-order byte of a 16-bit value. Because an address offset will be
        added to the value referred to in type 01 records it is also necessary to know the low-order value of the
        address as assembled. Addition may cause a carry to be added to the high-order byte. Type 10 for absolute
        logical and arithmetic instructions, and type 11 for absolute branch instructions.
        Each external reference has a 7-bit sequence number. There must be an ER-type ESD record for each
        sequence number used in RLD records.

9.1.5   Text records – TXT
         h'00'          length         offset high     offset low      code bytes...
        The length is the number of code bytes, up to a maximum of 28. The 2-byte offset indicates the start of these
        code bytes within the current section. If this TXT record is preceded by an RLD record then its code bytes will
        be adapted before they are copied into the executable module.
        The maximum of 28 bytes could have been extended to 32, the maximum offset possible in the 5 bits that are
        available in RLD instructions. Nevertheless available documentation states a maximum of 28.

9.1.6   End record– END
         h'FF'          entry high     entry low
        The 2-byte entry indicates the starting address of the executable, unless bit h'80' of the high byte is 1. A valid
        end record would therefore be h'ff,ff,ff'. The entry address is taken from the END directive. If more than one
        object file specifies an entry address then the address from the last object file is used. If no object file
        specifies an entry address, then the executable will start at the starting address of the first object file
        processed by the linker.



9.2     Relocation mechanism
        The following explains how the linker performs relocation, using examples.

        Preferred section address
        Typically an object file will be assembled at origin h'0000' indicating "don't care about my starting address".
        When an object file has an origin other than zero it means that it has a preference for that particular location
        in memory. If possible, the linker will use that preferred address. Sometimes it is not possible to satisfy a
82                                                                                     Relocation mechanism 9.2


preference, i.e. when previous object files processed by the linker already extend into the preferred memory
range. In that case the object file will need to be relocated.
As an example, assume that we have three object files. OB1 and OB2 are assembled at origin h'0000'; OB3 is
assembled at origin h'2120'. All object files are h'a0' in length. The linker commands are
         PHASE OUTF,h'2000' EXAMPLE PHASE
         INCLUDE OB1
         INCLUDE OB2
         INCLUDE OB3
OB1 will be placed at address h'2000' to h'209f'. OB2 will be placed at h'20a0' to h'213f'. OB3 cannot be
placed at h'2120' because that would overlap with OB2. It is therefore placed at the first possible location,
starting at h'2140'. All local absolute instructions within OB3 need to be relocated: the value h'20' needs to be
added to their addresses.
If OB3 had been assembled at a preferred address of h'2150' then relocation would not have been necessary,
and the linker would have inserted 16 bytes of padding between OB2 and OB3.

Page boundaries
No object file will be located so that it crosses a page boundary. If an object file will not fit in the remaining
space within the current 8 kilobyte page, then the entire object is translated to the start of the next page.

No relocation necessary
If relative instructions and immediate instructions do not refer to external symbols then relocation is not
necessary:
         05 08                    lodi,r1 8                      ; no relocation necessary
         CD 60 50        Loop     stra,r0 BUF,r1                 ; needs relocation
         F9 7B                    bdrr,r1 Loop                   ; no relocation necessary
          :                        :
                                  ORG       h'0050'
         00 00 00... BUF          RES       8
No relocation is necessary for the lodi and relative brach, nor for the 8 bytes that are reserved for the
buffer.

Local absolute instructions
Absolute instructions (like stra above) always need relocation even when local. When the linker has
determined a final address for the object module, that 13-bit address needs to be added to the bytes 60 50.
The stra instruction requires a corresponding RLD type 01 instruction for a local 13-bit address; the first
byte of that RLD instruction will be 100x-xxxx, with the x-bits indicating the offset of the second byte of
the stra instruction within its TXT record.

External absolute instructions
The situation is different when BUF is not defined in the same object but imported from another module:
                                  EXTRN   BUF
         CC 1F FF                 stra,r0 BUF-1
         CC 00 02                 stra,r0 BUF+2
In this case the assembler assumes the value zero for the location of BUF. The linker will know whether BUF
refers to an address (label) or to a constant.
If it is a constant, its 13 lower bits will need to be added to the values that are present in the binary object.
There must be exactly one other object file containing an ESD CD record with the name BUF.
If it is an address the final address of the object file in which BUF is defined, as well as the address of BUF
within that object. Or, if BUF is a constant, the value of that constant. The 13 lower bits of the final address
of the object file itself plus the final address of BUF plus will need to be added to the values that are present
in the binary object.
The stra instructions require a corresponding RLD instruction for an external 13-bit address; the first byte of
the RLD instruction will be 101x-xxxx, where the x-bits indicate the offset of the second byte of the stra
instruction within its TXT record. The second byte of the RLD instruction would be the sequence number
that was specified in the ESD ER record at the start of the object file.
There must be exactly one other object file containing an ESD CD or LD record with the name BUF.
